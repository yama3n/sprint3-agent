# 要件定義書: 引合書整理エージェント

> Vモデル: 要件定義 / 対応する検証: システムテスト
> 要求定義（01-request）を「何を作るか」に翻訳する。各機能の要件・スコープ・非機能要件を定義する。

> 出典の凡例:
> 【確定】01-requestで確定した要求、またはBootcamp課題資料に基づく確定要件
> 【提案】01-requestのKPI・ジャーニー、または本レビューでの議論から機能として具体化したもの
> 【仮説】要確認事項として扱う推測（要件として未確定）

## 2. 各機能の要件

### FUNC-01 書類アップロード・引合自動生成

- **概要**: 営業担当者は事前の案件作成や基本情報入力を行わず、顧客から届いた書類（xlsx / pdf / eml、複数ファイル・複数形式の混在）をそのままアップロードする。1回の新規アップロードを1つの引合として扱い、システムが引合ID（内部管理単位）を自動生成する。生成された引合の画面からは、担当者が明示的に「資料を追加」操作を行うことで、後から追加資料を同一引合に紐づけられる。AIが過去の既存引合と自動的に照合・統合する機能はScope 2とする（3章参照）。
- **事前条件**: なし（担当者がシステム画面にアクセスできること）。
- **正常フロー（新規）**: ①担当者が1つ以上の書類ファイルを一括アップロードする（形式混在可、事前の案件作成・名称入力は不要） → ②システムが新規の引合IDを自動生成する → ③AI処理（FUNC-02〜05）が自動的に開始される。
- **正常フロー（追加）**: ①担当者が既存の引合画面を開く → ②「資料を追加」操作で追加ファイルをアップロードする → ③同一引合に紐づけられ、AI処理が再実行される。
- **例外・バリデーション**:
  - 対応形式（xlsx / pdf / eml）以外のファイルはアップロード時に拒否し、理由を明示する。
  - 既存引合への資料追加は、担当者が対象の引合画面から明示的に「資料を追加」操作を行った場合にのみ行う。AIによる自動判定・自動統合（どの資料がどの既存引合に属するかをAIが推測する機能）は行わない。
  - ファイルサイズ・件数の具体的な上限値はMVPでは設定しない（4章参照）。
- **受入基準**:
  - 案件名・顧客名等の事前入力なしに、書類を一括アップロードするだけで引合IDが自動生成されること。
  - 1回のアップロードでxlsx・pdf・emlが混在した複数ファイルを一括アップロードでき、全ファイルが処理対象として同一引合に紐づくこと。
  - 生成済みの引合画面から「資料を追加」操作を行うと、追加ファイルが同一引合に紐づくこと。
  - 非対応形式のファイルをアップロードした場合、エラーメッセージとともにアップロードが拒否されること。

### FUNC-02 定義済み項目の抽出（引合情報・品目情報）

- **概要**: AIが項目を自由に生成するのではなく、あらかじめ定義された固定項目に対して資料から値を抽出する。項目は「A. 引合・案件全体の情報」と「B. 品目ごとの情報」の2階層で管理する。固定項目は、Bootcamp課題資料（`reference-local/r2b-webapp.vercel.app_assignments_sprint3.png`、「5. 最終アウトプット」＞「MVP機能」T1）で指定されている項目を**Bootcamp必須項目**として維持し、これに今回の議論で追加した**補助項目**、および「その他特記事項」等の**拡張項目**を加えた構成とする。3区分は表の「区分」列で明示する。

**その他の扱い**

- 固定項目に当てはまらないが営業担当者が把握すべき情報は、1件の巨大な自由記述としてではなく、`{項目内容, 出典}` の組を要素とする配列として複数保持する（例:「Mill Certificate提出必須」「第三者検査あり」「特殊コーティング指定」をそれぞれ独立した要素として保持）。
- 「案件全体のその他特記事項」（A-15）と「品目固有のその他条件」（B-9）は別のフィールドとして区別し、混在させない。

- **事前条件**: FUNC-01で引合に書類が紐づいていること。
- **正常フロー**: ①書類形式（xlsx/pdf/eml）を判定 → ②形式に応じた読込処理で本文・表構造を解析 → ③A（引合・案件全体）とB（品目ごと）の固定項目それぞれに値を抽出・マッピング → ④固定項目に当てはまらない情報を、A/Bどちらに属する特記事項かを区別した上で個別の特記事項として抽出 → ⑤抽出結果をFUNC-03に引き渡す。
- **例外・バリデーション**（業務ルール）:
  - 複数行に分かれた表見出しや、1セルに複数属性（例：外径×単重）が結合されている場合も、固定項目単位に分解して抽出すること。
  - メール等の記載更新については、明示的な訂正・変更の意図が読み取れる場合（例：「先ほどの数量240本ではなく320本でお願いします」）に限り、更新後の値を正として採用する。単に異なる値が複数箇所に記載されているだけで、どちらが正しいか本文から判断できない場合は、一方を自動的に採用せず「要確認」（FUNC-07）として扱う。「本文の後方に書かれた値を常に正とする」という一般ルールは採用しない。
  - 抽出できなかった固定項目は内部ステータス`missing`として保持する（ユーザー向け表示は「要確認」。理由`missing`はFUNC-07の内部理由としてInspector等で確認できる）。値を推測で埋めない。
- **受入基準**:
  - sample-dataのxlsx（見出し複数行・結合セルあり）から、B項目の主要項目（数量・外径・肉厚・長さ・グレード）が正しく抽出されること。
  - sample-dataのeml（本文末尾で数量の明示的な訂正がある例）で、訂正が明示的意図を持つ記述であることを条件に、訂正後の値（例：320本）が採用されること。
  - 単純に異なる値が複数箇所に存在し訂正の意図が読み取れないケースでは、値が自動確定されず「要確認」として保持されること。
  - 固定項目に当てはまらない情報が、案件全体／品目固有の区別を保った上で、複数の個別特記事項として（1件の自由記述にまとめられずに）保持されること。
  - 資料に記載のない固定項目は内部的に`missing`として扱われ、値が捏造されないこと。

### FUNC-03 構造化JSON生成（Single Source of Truth）

- **概要**: 引合内の複数資料から得られた抽出結果を、FUNC-02の固定項目スキーマ（A: 引合・案件全体情報、B: 品目ごとの情報）に沿って統合し、引合単位の構造化JSONを生成する。この構造化JSONを本システムにおけるデータの正本（Single Source of Truth）とし、以降のすべての画面表示・成果物生成はこのJSONを起点とする。基本フローは「元資料 → AI抽出 → 構造化JSON（確認中） → 担当者確認・修正 → 構造化JSON（確定済み） → 成果物生成」とする。内部ステータスとして`draft`/`final`を保持してよいが、ユーザー向け画面表示は「確認中」「確定済み」とする（4-2章・FUNC-05参照）。
- **事前条件**: FUNC-02による抽出結果が存在すること。
- **正常フロー**: ①各資料・各品目の抽出結果を統一スキーマにマッピング → ②同一引合内の複数資料に同一項目の情報が分散している場合は統合 → ③引合単位の構造化JSON（確認中状態）を生成する。
- **例外・バリデーション**:
  - 複数資料間で同一項目に異なる値があり、どちらが正しいか自動判断できない場合は、一方を採用せず両方の値と出典を保持し、FUNC-07の「要確認」対象とする。
  - 「確認中」状態のJSONは、担当者の確認・修正（FUNC-08）を経て初めて「確定済み」状態になる（FUNC-09）。成果物（Excel等）はJSONを直接編集して同期するのではなく、常にその時点の構造化JSONから生成・再生成する。
- **受入基準**:
  - 1引合・複数資料（xlsx＋pdf＋emlの組み合わせを含む）から、FUNC-02の固定項目スキーマに沿った構造化JSON（確認中状態）が1件生成されること。
  - 複数資料間で判断できない矛盾がある項目は、JSON上で両方の値と出典が確認できる状態で保持されること。
  - 担当者による修正（FUNC-08）がJSONに反映され、その修正後のJSONから成果物が再生成されること（Excelを直接編集してJSONと同期する経路が存在しないこと）。

### FUNC-04 Web検索による項目補完（公開情報限定）

- **概要**: 不明（`missing`）と判定された項目のうち、企業に関する公開情報や公開されている製品・規格情報など、Web上で客観的根拠を取得できる項目に限定してWeb検索による補完を行う。顧客固有の数量・希望納期・案件固有の要求仕様など、顧客資料以外から判断できない情報はWeb補完の対象外とし、「不明」のまま担当者確認（FUNC-08）に回す。
- **事前条件**: FUNC-03で不明（`missing`）項目が存在すること。
- **正常フロー**: ①不明項目のうち、公開情報から客観的に確認可能な種類の項目（例：依頼元企業の基本情報、公開製品規格）を対象として抽出 → ②Web検索により補完候補を取得 → ③補完した値を「Web補完」フラグとともに構造化JSONに反映する。
- **例外・バリデーション**:
  - 顧客固有の数量・希望納期・案件固有の要求仕様等は、Web検索による補完の対象としない。常に「不明」のまま保持し、担当者確認に回す。
  - Web検索でも情報が得られない場合は「不明」のまま維持し、補完を強制しない。
  - Web補完で得た値には、可能な範囲で「Web補完であること／参照元URL／参照元名称／参照日時」を保持する。
- **受入基準**:
  - Web補完された項目には、Web補完であることの区別情報に加えて、URL・参照元名称・参照日時（取得できた範囲）が付与されていること。
  - 顧客固有の数量・希望納期・案件固有の要求仕様が「不明」であった場合、Web検索によって自動的に値が埋められないこと。
  - Web補完不可の項目は「不明」のまま構造化JSONに残ること。

### FUNC-05 引合サマリー・成果物生成

- **概要**: 本機能の目的はExcelファイルを作ることそのものではなく、「どの会社から、何の案件について、どのような条件・品目で引合が来ているかを一目で把握できる状態を作ること」である。画面上で引合内容をサマリー表示するとともに、Excel形式のItem Listを出力する。
- **事前条件**: FUNC-03により構造化JSONのドラフト（確認中状態）が生成されていること（確定済みであることは前提としない。担当者確認前の確認中状態の段階でもサマリー表示・出力は可能とする）。
- **正常フロー**: ①構造化JSON（確認中／確定済みいずれの状態でも可）を取得 → ②「依頼元企業 → 案件情報 → 品目一覧 → その他特記事項 → 要確認項目」の順で画面上にサマリー表示する → ③Excel形式のItem Listを構造化JSONから生成し、ダウンロード可能にする。
- **例外・バリデーション**:
  - 不明（`missing`）項目のある品目についても出力自体は可能とし、該当箇所は「不明」と明示する（出力をブロックしない）。
  - ユーザー向け画面表示は「確認中」「確定済み」の2状態ラベルとする（英語のDraft/Finalは表示しない）。ダウンロードするExcel等の成果物ファイルのファイル名には、どちらの状態から生成されたかを判別できるよう`_draft`／`_final`等の接尾辞を付与する。
  - Excel等の成果物ファイルを直接編集しても構造化JSONには反映されない（成果物は常にJSONからの一方向生成）。
- **受入基準**:
  - 構造化JSONの内容が過不足なく画面サマリーおよびItem List（Excel）に反映されること。
  - 画面サマリーが「依頼元企業→案件情報→品目一覧→その他特記事項→要確認項目」の順で表示されること。
  - 不明項目のある品目についても、サマリー表示・Item List出力の両方が行えること。
  - 画面上の状態表示が「確認中」「確定済み」の日本語ラベルで行われ、出力ファイル名から`_draft`／`_final`のいずれかが判別できること。

### FUNC-06 抽出根拠の提示

- **概要**: 構造化データの各項目について、担当者が元資料を最初から読み直さなくても「なぜこの値になったのか」を短時間で確認できるよう、資料形式に応じた具体的な出典情報を提示する。
- **事前条件**: FUNC-02〜04により、各項目に出典情報が保持されていること。
- **正常フロー**: ①担当者が項目を選択 → ②その項目の出典を、資料形式に応じた形式で表示する。
- **出典情報の保持内容**（資料形式ごと、取得可能な範囲で）:
  - PDF: ファイル名、ページ番号、該当テキスト
  - Excel: ファイル名、シート名、セルまたはセル範囲
  - EML: ファイル名、件名／本文の該当部分
  - Web（FUNC-04によるWeb補完）: URL、参照元名称、参照日時
- **例外・バリデーション**:
  - 直接抽出・Web補完のいずれについても、出典情報が保持されていない項目が存在してはならない（信頼性KPI: 根拠確認可能率100%の前提条件）。
- **受入基準**:
  - AIが抽出・補完した全項目について、担当者が上記形式に応じた出典情報を確認できること。
  - PDF由来の項目についてページ番号・該当テキストが、Excel由来の項目についてシート名・セル位置が、それぞれ確認できること。

### FUNC-07 要確認項目の検知とアラート表示

- **概要**: 抽出結果を担当者向けに「✅ 確認不要 / ⚠️ 要確認」の2状態で分類・表示する。内部的には`missing`・`conflict`・`ambiguous`・`multiple_candidates`・`parse_error`等（要確認の理由）のステータスを保持してよいが、ユーザー向けの主表示は2状態に統一する。「不明」はユーザー向けの独立した表示ステータスではなく、`missing`という要確認理由の1つとして扱う。
- **事前条件**: FUNC-03（および該当する場合FUNC-04）による構造化JSONが存在すること。
- **正常フロー**: ①構造化JSONを走査し、各項目を「確認不要／要確認」のいずれかに分類する（要確認＝資料に情報が存在しない〔missing〕、または値は存在するがAIだけで確定すべきでない状態〔矛盾・複数候補・曖昧・パース失敗等〕） → ②要確認と判定された項目については、内部的な理由（missing・矛盾・複数候補・曖昧・パース失敗等）と候補値・出典を保持する（理由がmissingの場合、候補値は0件でよい） → ③一覧・サマリー画面上で2状態を視覚的に区別して表示し、要確認項目は理由・候補値・出典を確認できるようにする。
- **例外・バリデーション**:
  - 要確認と判定された項目は、いずれか一方の値を自動的に正としない（担当者の判断に委ねる）。
  - 「不明」「曖昧」「矛盾」等の内部理由をユーザー向けに別々のステータスとして表示しない（すべて「⚠️ 要確認」として統一表示し、詳細情報として理由を提示する）。
  - Web検索による補完（FUNC-04）は要確認理由には含めない。値の由来を示す別属性（Web補完フラグ・参照元情報）として保持する。
- **受入基準**:
  - 全項目が「確認不要／要確認」のいずれかに分類され、視覚的に区別された状態で一覧表示されること。
  - 要確認項目について、内部理由（不明〔missing〕・矛盾・複数候補・曖昧・パース失敗等のいずれか）が確認でき、値が存在する場合は対立する候補値およびそれぞれの出典が確認できること。
  - ユーザー向け画面上に「不明」「曖昧」「矛盾」等の個別ラベルが独立したステータスとして表示されないこと。

### FUNC-08 担当者による確認・修正（Human-in-the-Loop）

- **概要**: 担当者がシステム画面上で、AIが抽出した値・出典・要確認項目を確認し、必要な項目だけを修正する。目指す体験は「全部の資料を確認する」のではなく「AIが判断できなかった／怪しい箇所だけ確認する」ことである。担当者による修正は構造化JSONに反映され、それ以降の成果物は修正後のJSONから再生成される。
- **事前条件**: FUNC-03〜07により、構造化JSON（確認中状態）と根拠・検知結果が提示されていること。
- **正常フロー**: ①担当者がサマリー画面（特にFUNC-07で「要確認」と表示された項目）を確認 → ②必要に応じて値を修正 → ③修正内容が構造化JSONに反映される → ④以降の画面表示・成果物（FUNC-05）は修正後のJSONから再生成される。
- **例外・バリデーション**:
  - 担当者による修正値は、AIによる抽出・補完値と区別して記録する（どの値がAI抽出／Web補完／担当者修正のいずれであるかを追跡できるようにする）。
  - 担当者はJSONファイルを直接編集する必要はなく、画面UIからの操作のみで修正が完結する。
- **受入基準**:
  - 担当者が任意の項目を画面上で修正すると、構造化JSONに修正内容が反映されること。
  - 修正後にFUNC-05の成果物を再生成すると、修正内容が反映された内容で出力されること。
  - 修正が行われた項目について、修正前（AI抽出値／Web補完値）と修正後（担当者確定値）を区別して確認できること。

### FUNC-09 成果物確定

- **概要**: 担当者の確認・修正が完了した時点の構造化JSONとExcel成果物を、「確定済み」の成果物として保存・出力する。厳密なロック制御・確定解除操作・版管理はMVPの対象外とし、Scope 2以降で必要に応じて検討する。
- **事前条件**: FUNC-08による確認・修正が一通り完了していること。
- **正常フロー**: ①担当者が内容に納得した上で「確定」操作を行う → ②その時点の構造化JSONの状態が「確定済み」として保存される → ③「確定済み」JSONからExcel成果物（ファイル名に`_final`を付与）が生成・保存される。
- **例外・バリデーション**:
  - 確定後も再編集を妨げない（厳密な編集禁止・ロック・確定解除フローはMVPでは実装しない）。再編集が行われた場合、直近の「確定済み」状態との区別（版管理）はScope 2以降の課題とする。
- **受入基準**:
  - 「確定」操作を行うと、その時点の構造化JSONとExcel成果物が「確定済み」として保存・出力されること。
  - 画面上の状態表示が「確定済み」の日本語ラベルで表示され、出力されたExcelファイル名から`_final`（確認中の場合は`_draft`）が判別できること。

## 3. スコープ

各機能を優先度で4区分に振り分ける。

| 区分 | 意味 |
|------|------|
| **Scope 1（初版）** | まず必ず作る。MVPとして成立させる最小機能 |
| **Scope 2（改善）** | 初版の次に着手する改善・拡張機能 |
| **Scope 3（余裕があれば）** | 時間・リソースに余裕があれば実装する機能 |
| **Out of Scope** | 今回は明確に実装しないと決めたもの |

### Scope 1（初版）

MVPで最も重視する体験は「①資料をアップロード→②AIが企業・案件・品目情報を自動整理→③担当者が画面を見るだけで引合の全体像を理解→④要確認箇所だけ確認・修正→⑤確定→⑥Excel等の成果物を取得」という一気通貫フローである。

| 機能ID | 機能名 | 備考 |
|--------|--------|------|
| FUNC-01 | 書類アップロード・引合自動生成（1アップロード=1引合、追加資料は明示操作） | 案件作成レスの入口。一気通貫フローの起点。既存引合へのAI自動紐付け・引合統合はScope 2 |
| FUNC-02 | 定義済み項目の抽出（引合情報・品目情報） | 課題2（手作業の抽出・転記）を解決する中核機能 |
| FUNC-03 | 構造化JSON生成（Single Source of Truth） | 全機能のデータ基盤。「確認中」「確定済み」の区別を含む |
| FUNC-04 | Web検索による項目補完（公開情報限定） | 信頼性KPI（根拠確認可能率100%）の前提。対象を公開情報に限定した上で初版に含める |
| FUNC-05 | 引合サマリー・成果物生成（画面サマリー＋Excel出力） | Excel出力はBootcamp課題資料で指定されたItem Listのため必ずScope 1。PDF/Word出力はScope 2 |
| FUNC-06 | 抽出根拠の提示 | ジャーニー上の「ブレークスルー」に不可欠 |
| FUNC-07 | 要確認項目の検知とアラート表示 | 「怪しいところだけ確認すればよい」という体験の核 |
| FUNC-08 | 担当者による確認・修正（HITL） | Human-in-the-Loopとして必須 |
| FUNC-09 | 成果物確定（簡易版：ロック・確定解除・版管理なし） | ジャーニーの最終フェーズとして必須。厳密な制御はScope 2以降 |
| （UI要素） | 見積作成・発注メニューのComing Soon表示 | 実装対象ではなく、押せないことが明確なUI要素として将来構想を示すのみ（11章参照） |

### Scope 2（改善）

| 機能ID | 機能名 | 備考 |
|--------|--------|------|
| - | PDF出力 | FUNC-05の成果物形式拡張 |
| - | Word出力 | FUNC-05の成果物形式拡張 |
| - | AIによる既存引合への自動照合・紐付け、引合統合機能 | FUNC-01のMVPでは1アップロード=1引合の単純な方式とし、AIによる案件同一性判定・自動統合はScope 2に切り出す |
| - | 確定版のロック制御・確定解除フロー・版管理 | FUNC-09をMVPの簡易確定から厳密な確定管理へ拡張 |
| - | 修正履歴・監査ログの詳細表示 | FUNC-08の修正履歴保持を、担当者・マネージャー向けに閲覧可能な形で可視化する機能。IT／DX部門の監査可能性への期待に対応 |
| - | 引合一覧・進捗管理ダッシュボード | 複数引合を横断して処理状況（未確認／確認中／確定済み）を把握できる画面 |

### Scope 3（余裕があれば）

| 機能ID | 機能名 | 備考 |
|--------|--------|------|
| - | 抽出精度のフィードバックループ | 担当者による修正結果を学習・改善に活用する仕組み |
| - | 既存基幹システムとの連携（構造化JSON/Item Listのエクスポート・連携API） | IT／DX部門が期待する将来的な既存システム連携への布石 |

### Out of Scope（今回は実装しない）

| 項目 | 実装しない理由 |
|------|----------------|
| 見積書の自動作成 | 01-requestのユーザーゴールは引合整理・成果物確定までであり、見積作成は営業担当者の交渉・判断業務として残す対象。ただしUI上は「見積作成：今後対応予定」等のComing Soon表示として、押せないことが明確な形でメニューに存在させてよい（11章参照） |
| 仕入先・メーカーへの自動発注 | 調達・購買担当者の業務範囲であり、本Sprint3は営業担当者の引合整理業務に限定する。UI上は「発注：今後対応予定」のComing Soon表示として存在させてよい |
| 顧客・仕入先向け外部公開機能 | 01-requestで対象を営業担当者（Primary Persona）の社内業務に限定しているため |
| 営業事務・営業支援担当者向け専用機能 | Secondary Personaとして将来拡張候補とされているが、T社での役割分担が未確認【仮説】のため今回は対象外 |
| ID/パスワード認証・セッション管理・ロール／権限管理・SSO・マルチユーザー管理 | 今回はClaude Agent SDKを用いたローカル・単一ユーザーのPoCを前提とし、Bootcamp課題資料で明示的に要求されていない限りMVPの実装対象から外す。本番導入時の検討事項として別途整理する（4章参照） |

## 4. 非機能要件

| カテゴリ | 要件 |
|----------|------|
| 性能 | ファイル数・容量・PDFページ数等の具体的な上限値は、MVPでは設定しない。sample-dataで確認されたPDFのページ数は2〜7ページであった【観察】が、これはあくまで今回確認できたサンプルの事実であり、システムとして処理可能なページ数の上限として採用しない。PoCでは「提供されたsample-data 10件（xlsx/pdf/eml各形式を含む）を正常に処理できること」を性能面の検証対象とし、実運用上で必要となる上限値は、将来の利用実態確認後に別途定義する【未確定】。処理時間については、主要KPI（一次成果物作成時間50%以上削減）の達成を阻害しない範囲に収めることを目標とし、具体的な目安（例：1引合あたり数分以内）はPoCで検証する【仮説】 |
| セキュリティ（認証・認可方針） | 今回はClaude Agent SDKを利用したローカル・単一ユーザーのPoCを前提とし、ID/パスワード認証・セッショントークン管理・ロール／権限管理・SSO・マルチユーザー管理はMVPの実装対象外とする。本番導入時には、顧客資料を扱うことを踏まえた認証・権限設計が別途必要になる（IT／DX部門の期待事項として01-requestに記載）ため、その際の検討事項として整理する |
| 可用性 | ローカルPoCとして、担当者が利用する端末上で動作すること。稼働率等の定量目標はPoC段階では定めない【仮説】 |
| ユーザビリティ | Excel・メール・PDF等のOffice系ツールを日常的に使う一般的な業務ユーザー（AI・プログラミングの専門知識を前提としない）が、追加のトレーニングなしで「資料アップロード→サマリー確認→要確認箇所の修正→確定→成果物取得」の一連の操作を行えること |
| 保守性 | 引合ごとに書類フォーマットが異なる（見出し複数行、結合セル、自然文更新、英日混在等）状況に対し、抽出ロジックの追加・修正が個別ハードコードに頼らず行えるよう、AIによる抽出処理と業務ルール（例外・バリデーション、FUNC-02参照）を分離した構成とする |
