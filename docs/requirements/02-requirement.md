# 要件定義書: 引合書整理エージェント

> Vモデル: 要件定義 / 対応する検証: システムテスト
> 要求定義（01-request）を「何を作るか」に翻訳する。各機能の要件・スコープ・非機能要件を定義する。

> 出典の凡例:
> 【確定】01-requestで確定した要求から一意に導かれる機能
> 【提案】01-requestのKPI・ジャーニーから機能として具体化したもの
> 【仮説】要確認事項として扱う推測（要件として未確定）

## 2. 各機能の要件

### FUNC-01 案件作成・書類アップロード

- **概要**: 営業担当者が新規案件を作成し、顧客から受領した引合書類（xlsx / pdf / eml、複数ファイル・複数形式の混在）をその案件に紐づけて一括アップロードする。
- **事前条件**: 担当者が認証済みでシステムにログインしていること。
- **正常フロー**: ①案件を新規作成する（案件名・顧客名等の基本情報を入力） → ②案件に対して1つ以上の書類ファイルをアップロードする（形式混在可） → ③アップロード完了後、AI処理（FUNC-02〜05）が自動的に開始される。
- **例外・バリデーション**:
  - 対応形式（xlsx / pdf / eml）以外のファイルはアップロード時に拒否し、理由を明示する。
  - 同一案件への複数回・追加アップロードを許可する（後続資料の追加を想定）。
  - ファイルサイズ・件数の上限を超える場合はエラーとする（上限値は非機能要件で定義）。
- **受入基準**:
  - xlsx・pdf・emlを同一案件に混在させてアップロードでき、全ファイルが処理対象として案件に紐づくこと。
  - 非対応形式のファイルをアップロードした場合、エラーメッセージとともにアップロードが拒否されること。

### FUNC-02 資料読込・情報抽出

- **概要**: アップロードされた各書類をAIが読み込み、品目単位で必要項目（品名・規格・グレード・外径・肉厚・長さ・数量・納期等）を抽出する。
- **事前条件**: FUNC-01で案件に書類がアップロード済みであること。
- **正常フロー**: ①書類形式（xlsx/pdf/eml）を判定 → ②形式に応じた読込処理で本文・表構造を解析 → ③品目ごとに必要項目を抽出 → ④抽出結果をFUNC-03に引き渡す。
- **例外・バリデーション**（業務ルール）:
  - 複数行に分かれた表見出しや、1セルに複数属性（例：外径×単重）が結合されている場合も、項目単位に分解して抽出すること。
  - メール本文中で後から追記・訂正された値（例：本文末尾のP.S.で数量が上書きされる）がある場合、最新の記載を正として採用すること。
  - 抽出できなかった項目は「missing」として扱い、値を推測で埋めない（FUNC-04のWeb補完対象、またはFUNC-07の検知対象とする）。
- **受入基準**:
  - sample-dataのxlsx（見出し複数行・結合セルあり）から、主要項目（数量・外径・肉厚・長さ・グレード）が正しく抽出されること。
  - sample-dataのeml（本文末尾で数量が上書きされる例）で、上書き後の値（例：320本）が採用されること。
  - 資料に記載のない項目は空欄・missing扱いとなり、値が捏造されないこと。

### FUNC-03 構造化データ生成（JSON）

- **概要**: 案件内の複数資料から得られた抽出結果を、品目単位で統一スキーマの構造化JSONとして統合する。
- **事前条件**: FUNC-02による抽出結果が存在すること。
- **正常フロー**: ①各資料・各品目の抽出結果を統一スキーマにマッピング → ②同一案件内の複数資料に同一品目の情報が分散している場合は統合 → ③案件単位の構造化JSONを生成する。
- **例外・バリデーション**:
  - 複数資料間で同一項目に異なる値がある場合は、自動で一方を採用せず、矛盾として保持し（値を消さず両方保持し）FUNC-07で検知対象とする。
- **受入基準**:
  - 1案件・複数資料（xlsx＋pdf＋emlの組み合わせを含む）から、品目単位の構造化JSONが1件生成されること。
  - 複数資料間で矛盾する値がある場合、JSON上でその矛盾（両方の値と出典）が確認できる状態で保持されること。

### FUNC-04 Web検索による項目補完

- **概要**: 資料内に明記がなく欠落している項目について、Web検索により情報を補完する。
- **事前条件**: FUNC-03でmissing項目が存在すること。
- **正常フロー**: ①missing項目を検出 → ②Web検索により補完候補を取得 → ③補完した値を「Web補完」フラグ付きで構造化データに反映する。
- **例外・バリデーション**:
  - Web検索でも情報が得られない場合はmissingのまま維持し、補完を強制しない。
  - Web補完で得た値は、直接抽出した値と明確に区別可能な形でデータに保持する（フラグ・出典URL等）。
- **受入基準**:
  - Web補完された項目には「Web補完」であることを示す区別情報が付与されていること。
  - Web補完不可の項目はmissingのまま構造化データに残ること。

### FUNC-05 Item List生成（Excel出力）

- **概要**: 構造化JSONをもとに、社内標準フォーマットのItem List（Excel）を生成する。
- **事前条件**: FUNC-03（および該当する場合FUNC-04）による構造化データが確定していること。
- **正常フロー**: ①構造化JSONを社内標準のItem Listフォーマットにマッピング → ②Excelファイルとして生成し、案件に紐づけて保存・ダウンロード可能にする。
- **例外・バリデーション**:
  - 必須項目がmissingのままの品目がある場合も出力自体は可能とし、該当セルは空欄または明示的なmissing表示とする（出力をブロックしない）。
- **受入基準**:
  - 構造化JSONの内容が過不足なくItem List（Excel）の対応セルに反映されること。
  - missing項目のある品目についても、Item Listが出力できること。

### FUNC-06 抽出根拠の提示

- **概要**: 構造化データの各項目について、抽出元資料・該当箇所、またはWeb補完である旨を担当者が確認できるようにする。
- **事前条件**: FUNC-02〜04により、各項目に出典情報（資料名・該当箇所、またはWeb補完フラグ）が保持されていること。
- **正常フロー**: ①担当者が項目を選択 → ②その項目の出典（元資料の該当箇所、またはWeb補完の旨）を表示する。
- **例外・バリデーション**:
  - 出典情報が保持されていない項目が存在してはならない（直接抽出・Web補完のいずれについても出典情報の記録を必須とする＝信頼性KPIの前提条件）。
- **受入基準**:
  - AIが抽出・補完した全項目について、担当者がその根拠（資料の該当箇所、またはWeb補完である旨）を確認できること（信頼性KPI: 根拠確認可能率100%の判定基準）。

### FUNC-07 missing・曖昧・矛盾項目の検知とハイライト

- **概要**: 必須項目の欠落（missing）、複数資料間で値が矛盾する項目、記載内容が曖昧な項目を自動検出し、一覧上で強調表示する。
- **事前条件**: FUNC-03（および該当する場合FUNC-04）による構造化データが存在すること。
- **正常フロー**: ①構造化データを走査し、missing／矛盾（FUNC-03で保持された複数値）／曖昧（信頼度が低い抽出等）を判定 → ②該当項目を一覧上で区別可能な形で強調表示する。
- **例外・バリデーション**:
  - 矛盾がある項目は、いずれか一方を自動的に正としない（担当者の判断に委ねる）。
- **受入基準**:
  - missing・矛盾・曖昧のいずれかに該当する項目が、通常項目と視覚的に区別された状態で一覧表示されること。
  - 矛盾項目については、対立する両方の値と、それぞれの出典が確認できること。

### FUNC-08 担当者による確認・修正

- **概要**: 担当者が構造化データ／Item Listの内容を画面上で確認し、誤りや不足している項目を修正できる。
- **事前条件**: FUNC-03〜07により、構造化データと根拠・検知結果が提示されていること。
- **正常フロー**: ①担当者が一覧（特にFUNC-07でハイライトされた項目）を確認 → ②必要に応じて値を修正 → ③修正内容が構造化データおよびItem Listに反映される。
- **例外・バリデーション**:
  - 担当者による修正値は、AIによる抽出・補完値と区別して記録する（修正履歴・修正者情報を保持し、後から「誰がいつ確定値にしたか」を追跡できるようにする）。
- **受入基準**:
  - 担当者が任意の項目を修正すると、構造化データとItem Listの双方に修正内容が反映されること。
  - 修正が行われた項目について、修正前（AI抽出値）と修正後（担当者確定値）を区別して確認できること。

### FUNC-09 成果物確定

- **概要**: 担当者の確認・修正が完了した構造化データおよびItem Listを、確定版として保存する。
- **事前条件**: FUNC-08による確認・修正が完了していること。
- **正常フロー**: ①担当者が内容に納得した上で「確定」操作を行う → ②その時点の構造化データ・Item Listが確定版として保存される → ③確定後は原則編集不可とする。
- **例外・バリデーション**:
  - 確定後に修正が必要な場合は、明示的な「確定解除」操作を経てから再編集可能とする（誤操作による確定版の意図しない書き換えを防止する）。
- **受入基準**:
  - 「確定」操作後、その時点の構造化データ・Item Listが確定版として保存され、通常操作では編集できない状態になること。
  - 確定解除操作を経ずに確定版の内容が変更されないこと。

## 3. スコープ

各機能を優先度で4区分に振り分ける。

| 区分 | 意味 |
|------|------|
| **Scope 1（初版）** | まず必ず作る。MVPとして成立させる最小機能 |
| **Scope 2（改善）** | 初版の次に着手する改善・拡張機能 |
| **Scope 3（余裕があれば）** | 時間・リソースに余裕があれば実装する機能 |
| **Out of Scope** | 今回は明確に実装しないと決めたもの |

### Scope 1（初版）

| 機能ID | 機能名 | 備考 |
|--------|--------|------|
| FUNC-01 | 案件作成・書類アップロード | 一気通貫フローの入口として必須 |
| FUNC-02 | 資料読込・情報抽出 | 課題2（手作業の抽出・転記）を解決する中核機能 |
| FUNC-03 | 構造化データ生成（JSON） | Item List生成・根拠提示の前提となるデータ基盤 |
| FUNC-04 | Web検索による項目補完 | 信頼性KPI（根拠確認可能率100%）が直接抽出・Web補完両方を前提とするため初版に含める |
| FUNC-05 | Item List生成（Excel出力） | 主要成果物。ユーザーゴールの中心 |
| FUNC-06 | 抽出根拠の提示 | ジャーニー上の「ブレークスルー」に不可欠。これがないとFUNC-08の確認作業が資料の読み直しに戻ってしまう |
| FUNC-07 | missing・曖昧・矛盾項目の検知とハイライト | 「怪しいところだけ確認すればよい」という体験の核 |
| FUNC-08 | 担当者による確認・修正 | Human-in-the-Loopとして必須 |
| FUNC-09 | 成果物確定 | ジャーニーの最終フェーズとして必須 |

### Scope 2（改善）

| 機能ID | 機能名 | 備考 |
|--------|--------|------|
| - | 修正履歴・監査ログの詳細表示 | FUNC-08の修正履歴保持を、担当者・マネージャー向けに閲覧可能な形で可視化する機能。IT／DX部門の監査可能性への期待に対応 |
| - | 案件一覧・進捗管理ダッシュボード | 複数案件を横断して処理状況（未確認／確認中／確定済み）を把握できる画面 |

### Scope 3（余裕があれば）

| 機能ID | 機能名 | 備考 |
|--------|--------|------|
| - | 抽出精度のフィードバックループ | 担当者による修正結果を学習・改善に活用する仕組み |
| - | 既存基幹システムとの連携（Item Listのエクスポート/連携API） | IT／DX部門が期待する将来的な既存システム連携への布石 |

### Out of Scope（今回は実装しない）

| 項目 | 実装しない理由 |
|------|----------------|
| 見積書の自動作成 | 01-requestのユーザーゴールはItem List確定までであり、見積作成は営業担当者の交渉・判断業務として残す対象 |
| 仕入先・メーカーへの自動発注 | 調達・購買担当者の業務範囲であり、本Sprint3は営業担当者の引合整理業務に限定する |
| 顧客・仕入先向け外部公開機能 | 01-requestで対象を営業担当者（Primary Persona）の社内業務に限定しているため |
| 営業事務・営業支援担当者向け専用機能 | Secondary Personaとして将来拡張候補とされているが、T社での役割分担が未確認【仮説】のため今回は対象外 |
| SSO等の高度な認証基盤との連携 | 非機能要件で定める基本的な認証方式で初版は成立させ、外部IdP連携は将来課題とする |

## 4. 非機能要件

| カテゴリ | 要件 |
|----------|------|
| 性能 | 1案件あたりの書類（xlsx/pdf/eml混在、最大7ページ程度のPDFを含む）をアップロードしてから構造化JSON・Item Listが生成されるまでの処理時間は、主要KPI（一次成果物作成時間50%以上削減）の達成を阻害しない範囲に収める。目安として1案件あたり数分以内を目標とする【仮説・PoCで検証】 |
| セキュリティ（認証・認可方針） | 認証方式: ID/パスワードによるログイン認証を基本とする（外部IdP連携はOut of Scope）／トークン有効期限: セッショントークンは一定時間（例: 8時間、営業時間内の利用を想定）で失効し再認証を要求する【仮説】／権限モデル: 営業担当者ロールが自身の案件を作成・確認・確定できる。ロールを跨いだ他者案件へのアクセス制御は将来のマルチユーザー運用時に詳細化する【仮説】 |
| 可用性 | 営業時間内（平日日中）にシステムが継続的に利用可能であること。PoC期間中の具体的な稼働率目標は定めない【仮説】 |
| ユーザビリティ | Excel・メール・PDF等のOffice系ツールを日常的に使う一般的な業務ユーザー（AI・プログラミングの専門知識を前提としない）が、追加のトレーニングなしで案件作成〜確認・修正〜確定の一連の操作を行えること |
| 保守性 | 案件ごとに書類フォーマットが異なる（見出し複数行、結合セル、自然文更新、英日混在等）状況に対し、抽出ロジックの追加・修正が個別ハードコードに頼らず行えるよう、AIによる抽出処理と業務ルール（例外・バリデーション）を分離した構成とする |
