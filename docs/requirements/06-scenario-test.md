# シナリオテスト仕様書: 引合書整理エージェント

> Vモデル: システムテスト（右側）/ 対応する設計: ② 要件定義
> `01-request.md` 〜 `05-api-ipo.md` および `mocks/mockup.html` を正として、Build後の実アプリが要件を満たしているかを検証する。
> 研修生は **Build した実アプリ** に対して手動でシナリオを実行し、判定を記録する。

## 使い方（研修生向け）

1. Build した実アプリを起動する（前提環境を満たす）
2. シナリオを上から順に実行し、各ステップの期待結果と一致するか確認する
3. 判定欄に ☐Pass / ☐Fail を記録する（Fail はメモに事象を残す）
4. Fail は原因を **要件(②)・設計(③〜⑤)・実装(Build)** のどこかに切り分けて修正する
5. 各シナリオ末尾の「合格条件」を満たせば、そのシナリオは合格
6. 全シナリオ Pass ＝ 要件を満たしたことの証明

## 前提環境

| 項目 | 内容 |
|------|------|
| 対象 | Build した実アプリ（ローカル起動。URLは研修生の実行環境に依存、例: `http://localhost:3000`） |
| テストデータ | `sample-data/` 配下の10ファイル（本書「3. sample-dataとの対応」参照）。各ファイルは架空の企業・案件を扱う研修用データ |
| 初期状態 | `sales@toseki-steel.co.jp` でログイン可能な単一ユーザーアカウントが作成済み。引合は0件（クリーンな状態）から開始する。各シナリオの「前提条件」に、直前のシナリオで作成した引合を再利用する場合はその旨を明記する |
| 未対応形式の確認用ファイル | `.docx` 等、対応3形式（xlsx/pdf/eml）以外の任意のファイルを1つ用意する（TEST-15用） |

## 4. 未カバー要件・既知の限界

- **強制停止（stopped）の再現性**: agent-plan.mdの強制停止しきい値（ツール呼び出し数・タイムアウト秒数）は【仮説】の暫定値であり、実際のBuild実装でどの入力が確実にしきい値へ到達するかは実測しないと分からない。TEST-18は「到達させる入力を用意できない場合はコードレビューで代替可」としているが、これは実機能テストとしては弱い代替であり、実測後に確実な再現手順（例: 意図的に大量の品目を含むxlsxを用意する）へ差し替えることが望ましい。
- **Web補完の正確性そのもの**: TEST-09/TEST-10は「一意特定できた場合は自動採用しない／URL等が付与される」という**手続き・ガードレールの正しさ**を検証するものであり、Web検索エージェントが実際にどの事実を返すかは外部情報源に依存し非決定的である。個々の検索結果の事実的正確性（例: 実在しない架空企業名に対する検索結果の扱い）は、本シナリオテストの対象外とする。
- **性能・スケール**: 02-requirement.md 4章は「ファイル数・容量・ページ数の上限値はMVPでは設定しない」としているため、本書も大量データ・大容量ファイルでの性能検証シナリオは含めていない。
- **追加アップロードの複雑な統合ケース**: TEST-13/TEST-14は単純化した1項目のケースのみを扱う。複数項目が同時に競合するケースや、品目行の増減（既存品目にない新品目が追加アップロードで検出された場合の扱い）は、agent-plan.md自体にも詳細ルールがなく、本書でも未カバーである。
- **修正履歴・監査ログ**: 02-requirement.mdでScope 2とされているため、本書でも対象外。

## 5. Build開始前に解消すべき事項

現時点でBuildを妨げる致命的な設計不備は見つかっていない。ただし、以下はBuild時に実装者が迷わないよう、着手前に決めておくことを推奨する。

1. **TEST-18（強制停止）の具体的な再現データ**: しきい値が【仮説】のままBuildへ進むと、このシナリオだけは「実装が完了しないとテストデータを作れない」状態になる。Build初期に実測してしきい値を確定し、それに応じたテストデータ（品目数・ファイルサイズ等）を用意する。
2. **TEST-04/TEST-14で使う「追加資料」の最終確定**: 本書はTEST-14の追加アップロード用データを「sample-08のRev.2訂正記載、または任意に用意した想定資料」と暫定的にしているが、実データの数量が既存確定値と綺麗に競合するとは限らないため、Build時に確定済み値と意図的に異なる値を含む追加ファイルを1件、研修生側で用意しておくとテストがスムーズになる。
3. **sample-data 10ファイルはすべて別々の架空企業のデータ**であることを研修生に周知する。TEST-03のように複数ファイルを1つの引合として一括アップロードする異常系シナリオでは、依頼元企業が資料ごとに異なり「要確認（矛盾）」になることが**仕様通りの正しい挙動**である。これを想定外のバグと誤認しないよう、実行前にこの前提を共有しておく。
